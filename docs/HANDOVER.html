The platform finds newly published vulnerabilities, works out which of your GitHub repositories are affected, asks an LLM for the smallest dependency fix, proves that fix inside a locked-down Docker sandbox, and opens a pull request. People review and merge it. The bot never merges.

What we are building

The problem. Dependencies get vulnerabilities published against them every day. For a company with many repositories, finding which ones are affected, deciding what to change, testing that the change is safe and getting a pull request in front of the right reviewer is slow, repetitive work, so fixes wait weeks.

The solution. A service that does everything up to the review. It watches the public vulnerability feeds, checks every one of your GitHub repositories, has an LLM propose the smallest possible fix (almost always a version bump), then proves the fix in a throw-away Docker sandbox by running the repository's own tests and a vulnerability scanner. Only a fix that passes becomes a pull request, addressed to the people who own the code. Humans stay in charge: they review and merge, and the bot cannot merge.

What a developer sees

  • A pull request titled fix(medium): CVE-2024-35195 bump requests 2.31.0 → 2.32.0, with the test results before and after, a confidence score, and links to the audit page and JIRA ticket.
  • A Teams message, and a JIRA ticket for Critical and High CVEs.
  • Nothing at all for CVEs that do not affect them, or that the system could not fix safely.

What it deliberately does not do

  • Merge anything, or touch CI configuration (workflow files are hard-denied).
  • Raise a PR it could not prove: failing baseline tests, no tests, or a CVE still reported all stop it.
  • Rewrite application code on its own initiative. It makes the minimal change that clears the CVE.
  • Act on text found in a repository or advisory as if it were an instruction.

Architecture

Two cooperating pipelines share one database. The detection pipeline is ordinary Celery code. The fix agent is a LangGraph state machine that runs once per CVE and repository.

End-to-end flow

  1. 06:00 UTC scan.sync_cves reads NVD changes since the saved cursor, enriches each with OSV, and stores the ones that touch a supported ecosystem.
  2. 02:00 UTC scan.regenerate_sboms syncs the organisation's repositories, then queues one scan.generate_sbom per in-scope repo (shallow clone, Syft, archive to S3, row in PostgreSQL).
  3. After either, the matcher evaluates every triaged CVE against every repo's newest SBOM, writes cve_repo_impact, creates one QUEUED job per CVE and repo (most urgent first, capped), and queues remediation.run_fix_agent.
  4. A remediation worker takes the per-repo Redis lock, claims the job (QUEUED→RUNNING), creates the Confluence page and JIRA ticket so the PR can link to them, then runs the graph.
  5. The graph assembles context, checks reachability, asks the LLM for a fix, scores it, validates it in a sandbox (baseline tests, patch, reinstall, tests again, vulnerability scan), and loops back to the LLM with the failure if any step fails.
  6. A fully validated fix becomes a pull request (one atomic commit, labels, CODEOWNERS reviewers). Owners are notified. write_audit persists the event trail and queues the Confluence/JIRA refresh.
  7. Reviewers act on GitHub. The pull_request closed webhook records the outcome (merged clean, merged with edits, closed unmerged), updates the job, notifies, and feeds the weekly confidence calibration.

Two design rules to keep

1. The LLM is used in exactly one place (generate_fix). Everything else, including GitHub access, is deterministic code. 2. Nodes only return the fields they changed; conditional edges are pure functions of the state. This is what makes every node unit-testable with a plain state object.

What would have happened if something failed

Tests regress: the failure output goes back to the model and it tries again. Dependency conflict: same. The scanner still sees the CVE: same. Three failures: the job ends BLOCKED, no PR is raised, and the audit trail says why. The golden cases regression_blocks, wrong_fix_blocks and vendored_copy run exactly those paths.

The fix agent

Defined in src/agent/graph.py. State is a Pydantic model (AgentState) checkpointed to PostgreSQL after every step with thread_id = job_id. Dashed nodes run inside the sandbox.

The repair loop

This is what makes it an agent rather than a one-shot prompt. When the patch does not apply, dependencies do not resolve, tests regress, or the scanner still sees the CVE, the failing node records the reason and the router sends the run back to generate_fix. The next prompt carries the previous attempts and their failure output (as untrusted data). The sandbox is reused and reset (git checkout -- . && git clean -fd). The limit is MAX_FIX_ATTEMPTS (default 3); after that the job ends BLOCKED and no PR is raised.

Defences against hostile input

CVE text, changelogs and repository files are attacker-influenceable, so:

  • Untrusted text is wrapped in <untrusted_data> tags; any tag the content tries to inject is escaped, and the system prompt says to treat the contents as data.
  • Every file path the model returns must be inside the repo, free of .. and absolute paths, on the list of files actually sent, and never under .git/ or .github/workflows/ (hard-denied even if allowlisted).
  • original_content must appear exactly once in the file the model was shown; identical old and new content is rejected.
  • Secrets are redacted before they reach the prompt, the state, the audit events, Confluence or the PR (src/core/redaction.py).
  • The sandbox has no network and no credentials; the GitHub token is used only on the host.

Checkpoints, resume, pause

  • A crash resumes from the last finished node. The runner resumes only when the checkpoint belongs to the same run_id; a re-queued job gets a new run_id and starts fresh.
  • Pause is cooperative: the runner checks the job status after each graph step, stops, removes the sandbox and rewinds to sandbox creation if the next step needed it. A long-running node delays a pause. Resume rebuilds the input from the stored JOB_QUEUED event.
  • LangGraph's default recursion limit (25) is too low for three repair attempts, so graph.RECURSION_LIMIT is 100.

Detection pipeline

1 · CVE feed src/services/cve_aggregator/, src/services/pipeline.py

  • sync_cves reads NVD CVEs modified since the cursor stored in sync_state['cve_sync'] (first run: last 24 hours; each run re-reads 10 minutes before the cursor; windows are split at 119 days because NVD refuses more than 120).
  • Each CVE is merged with OSV. OSV's CVE record usually only has git ranges. The package versions and fixes are on its aliases (GHSA-…, GO-…, PYSEC-…), which the aggregator fetches and merges. NVD is authoritative for CVSS and KEV, OSV for affected ranges and fixes.
  • A CVE is stored only if it has an affected package in one of the six supported ecosystems (npm, pip, maven, go, nuget, gem). CVEs that fail to process are remembered in the cursor's retry_ids and fetched again next run.
  • NVD allows 5 requests per 30 seconds without an API key and 50 with one. Set NVD_API_KEY in production.

2 · Triage src/services/triage/prioritiser.py

Priority from CVSS v3 (Critical ≥ 9, High ≥ 7, Medium ≥ 4, Low), ranked KEV first, then score, then age. CVEs below MIN_CVSS_THRESHOLD or without a score are dropped (they return on a later sync once NVD scores them), except KEV CVEs, which are always kept.

3 · SBOM src/services/sbom/generator.py

  • Shallow clone on the host, syft dir:… -o cyclonedx-json, archive the document to s3://$S3_BUCKET_SBOM/{repo}/{commit}.cdx.json, and keep a row per generation in sboms (history is kept; the newest row is current).
  • Only remediable components are kept: supported ecosystem, an exact version (flask>=2.0 is ignored) and declared in a file a PR can edit. A manifest wins over a lockfile. Packages seen only as installed metadata are ignored.
  • Syft must be on the worker's PATH (or SYFT_BIN). A pinned, checksum-verified copy for local use lives in .tools/ (git-ignored).

4 · Matcher src/services/matcher/vulnerability_matcher.py

  • Ranges come from OSV as strings such as < 1.4.9, >= 2.0.0, < 2.0.3, <= 3.1.0, all versions.
  • The safe version is the smallest known fix that clears every range containing the installed version, so 2.0.1 goes to 2.0.3, not down to 1.4.9. If no usable fix exists the match is counted (no_fix) and no job is created.
  • Package names are compared after normalisation (PEP 503 for pip, lower-case elsewhere), so Jinja2 matches jinja2.
  • One job per {cve, repo} pair (unique constraint uq_job_cve_repo). Jobs are created most urgent first and capped by MAX_NEW_JOBS_PER_RUN (50) to protect LLM spend; the rest wait for the next run.
  • Impacts no longer present in a repo's newest SBOM are deleted on a full run. Messages are sent after the database commit so a worker never sees a job that is not there yet.
  • The full agent input is stored in the JOB_QUEUED audit event; the Control API uses it to resume a paused job.

GitHub and pull requests src/services/github/

  • PyGithubContentSource reads files, code search and release notes (via the package's upstream repo, resolved from PyPI, npm or the Go module path). PyGithubPullRequestService writes.
  • A PR is one atomic commit through the Git Data API (blobs, tree, commit, ref), based on the default branch's current head with the validated section replacements re-applied. If the base moved so the section no longer matches exactly once, the job fails instead of committing something untested.
  • Branch fix/cve-{CVE}-{repo}-{YYYYMMDD} (a numeric suffix if taken). Labels from PR_LABELS plus severity:<level>, created if missing. Reviewers: owners of the changed files from CODEOWNERS (.github/CODEOWNERS, CODEOWNERS, docs/CODEOWNERS; last matching rule wins), falling back to repo admins. An invalid reviewer is a warning, not a failure.
  • Dedup guard: an open PR whose branch starts with the bot prefix for the same CVE is reused or skipped. A hidden marker <!-- cve-remediation-bot job_id=… --> in the body ties a PR to its job. A failed PR creation deletes the branch it pushed.
  • Text from the model or the CVE is sanitised before it enters the PR body (HTML, @mentions, #123 references and image embeds are neutralised).
  • Branch protection is reported, not enforced: the bot cannot merge, but protection and required CODEOWNERS review must be configured on the target repos by you.
  • PyGithub paces itself (GITHUB_SECONDS_BETWEEN_REQUESTS 0.25 s, …_WRITES 1 s), so a PR takes about ten seconds. Rate limits and 5xx are retried with backoff.

Confidence calibration src/services/calibration.py, src/services/pr_outcomes.py

The pull_request closed webhook records MERGED_CLEAN, MERGED_EDITED (more than one commit, so a human added to the branch) or CLOSED_UNMERGED in pr_outcomes next to the score the PR was raised with. A closed-unmerged PR marks the job BLOCKED so it is never raised again. A PR is attributed to a job only if the branch prefix, the body marker, the repository and the PR number all match (a pasted marker alone is not trusted). Weekly, audit.recalibrate_confidence moves the HIGH and MEDIUM cut-offs to the lowest scores whose own band was merged clean at least 90% and 70% of the time. It needs 30 reviewed PRs and 10 per band, and keeps the defaults otherwise.

The remediation task

  • Lock first, then claim. It takes cve-remediation:repo-lock:<repo> (TTL 3 h) so two jobs never race PRs on one repo, then atomically moves the job QUEUED→RUNNING. A duplicate or redelivered message finds the job not queued and exits.
  • Lock busy: retry in 5 minutes, up to 36 times. This does not use up the failure budget.
  • Failure: up to 3 retries with exponential backoff. Because the graph is checkpointed, a retry resumes at the failed step and never repeats a finished PR or LLM call. After the last retry the job is marked FAILED instead of staying RUNNING.
  • Soft time limit 3 h, hard limit 3 h 10 min. The Redis visibility_timeout is 4 h, which must stay above the hard limit, otherwise Redis redelivers a still-running task.
  • AUTOMATION_ENABLED=false makes the task skip the job (it stays QUEUED) and the matcher skip creating jobs.

Three traps

Clocks: job timestamps come from the database clock, so tests that pass a fake now to the matcher must keep it near the real time. Retries sleep for real unless a test patches asyncio.sleep in src.utils.retry; an unpatched test that retries takes seconds. The real-internet tests can flake: the Docker tests that install from PyPI skip or fail when the network is unavailable (one did during the final run and passed on rerun). Rerun before suspecting the code.

Golden-CVE evaluation tests/eval/

Each case in cases/<name>/ is a tiny repository, an advisory and the outcome a correct system must produce. The harness runs the real graph (real Docker sandbox, PyPI install, pytest and Grype); only GitHub and the database are in memory. The model is either replay (recorded answers, deterministic, tests everything around the model) or live (your endpoint, tests the model). Checks are quality (outcome, attempts, confidence, diff size, scanner) or safety (no PR where none is allowed, only expected files change, forbidden files untouched, secrets absent from prompts, PR and audit, no container left behind). Any safety failure fails the gate whatever the pass rate; thresholds are in gate.yaml (replay 100%, live 80%).

Runbook

Commands assume the Control API at $API with $API_KEY, and PostgreSQL/Redis reachable with psql / redis-cli.

Stop everything safely

Set AUTOMATION_ENABLED=false and restart the API and workers (settings are read at start-up). No new jobs are created and queued jobs are skipped but stay QUEUED. A run already in progress is not interrupted (the switch is checked when a run starts); pause it through the API if it must stop. Turn it back on and the matcher re-queues what was lost (a queued job older than 6 hours is re-sent).

Follow one job

curl -s -H "X-API-Key: $API_KEY" $API/api/v1/jobs/$JOB_ID                 # status, audit events, links
curl -s -H "X-API-Key: $API_KEY" $API/api/v1/jobs/$JOB_ID/graph-trace     # which node ran, what runs next
# logs are JSON with job_id on every line:
grep '"job_id": "'$JOB_ID'"' worker.log

A job is stuck in RUNNING

Normal: the task is still working (three attempts can take half an hour). Abnormal: no worker is processing it. The task marks a job FAILED after its retries, but a hard-killed worker can leave it RUNNING; there is no watchdog yet.

select job_id, repo_name, cve_id, updated_at from remediation_jobs where status = 'RUNNING' and updated_at < now() - interval '4 hours';
-- confirm nothing holds its repo:   redis-cli get cve-remediation:repo-lock:org/repo
update remediation_jobs set status = 'FAILED' where job_id = '...';   -- the matcher retries it after FAILED_JOB_RETRY_AFTER_HOURS

Re-run a BLOCKED or NOT_REACHABLE job

Those statuses are final on purpose (a human or a rule decided). To retry one deliberately, make it look like an old failure so the next matcher run re-queues it:

update remediation_jobs set status = 'FAILED', updated_at = now() - interval '25 hours' where job_id = '...';

Locks, slots, containers

redis-cli del cve-remediation:repo-lock:org/repo               # repo lock left by a killed worker (it expires after 3 h anyway)
redis-cli zrange cve-remediation:sandbox-slots 0 -1 withscores   # live sandbox leases
redis-cli del cve-remediation:sandbox-slots                       # only if you are sure no sandbox is running
docker ps -a --filter label=cve-remediation.sandbox=1             # sandboxes (label cve-remediation.job_id names the job)
docker rm -f $(docker ps -aq --filter label=cve-remediation.sandbox=1)
redis-cli llen remediation                                        # queue depth (also: scanning, notifications, audit)

Sandbox image

Rebuild at least daily in production (CI): the Grype database is part of the image and is not updated at run time. A new Grype release can also change the database schema, which is why GRYPE_VERSION is pinned in the Dockerfile and was bumped from 0.86.1 to 0.120.1.

docker build --no-cache -f docker/sandbox/python.Dockerfile -t cve-sandbox-python docker/sandbox

Other routine tasks

  • Exempt a repo: add the cve-exempt topic on GitHub, or PATCH /api/v1/config/repos with a blocklist.

How to change things

Step-by-step recipes for the changes you are most likely to make.

Add a graph node
  1. Create src/agent/nodes/<name>.py with @agent_node("name") async def name(state) -> dict. Return only changed fields, and add your audit event with with_event / make_event. Repairable failures return record_failure(state, reason); unexpected ones raise (the decorator turns them into FAILED).
  2. Export it in src/agent/nodes/__init__.py, add a pure route_after_<name> to routing.py (with a test in tests/unit/agent/test_routing.py), and register node and edges in graph.py.
  3. Reach external systems only through src/agent/deps.py so tests can substitute them. Add the state fields to AgentState.
  4. Extend a scenario in tests/integration/test_graph_repair_loop.py or test_graph_pr_flow.py and, if behaviour changes, a golden case.
Add an ecosystem (for example npm)
  1. Sandbox: a Dockerfile under docker/sandbox/, an entry in _IMAGES in docker_sandbox.py and a setting for the image.
  2. Replace the pip-only pieces: _pip.py (install command), test_runner.py (command and output parser; the node is hard-wired to pytest today), dependency_resolver.py (version check), security_scanner.py (scan targets), sandbox_executor.py (the ecosystem guard).
  3. Analysis: a reachability analyser in reachability.py, import names in src/utils/packages.py, the search language map in context_assembler.py.
  4. Matching already works (SBOM purl mapping, name canonicalisation, range evaluation). Add golden cases for the new ecosystem before trusting it.
Add a notification channel
  1. Subclass NotificationHandler in src/services/notifications/<channel>.py (name, supports(), send() that raises on failure).
  2. Register it in HANDLERS in dispatcher.py, add its settings (see below), and list it in ENABLED_NOTIFICATION_CHANNELS.
  3. Add a payload schema to tests/contract/schemas.py and a test that validates what the handler sends. Idempotency and logging come from the dispatcher.
Add a golden case
  1. Create tests/eval/cases/<name>/ with repo/ (the files), case.yaml (advisory, job and expect), and llm_responses.json (the model answers to replay, in order; the last repeats).
  2. Use replay_only: true for scripted bad behaviour. Pick packages that install on Python 3.12 (an old urllib3 does not).
  3. Run python -m tests.eval.run --cases <name>. tests/unit/test_eval_harness.py checks that every recording is valid model output.
Add a setting
  1. Add the typed field to Settings in src/core/config.py; secrets are SecretStr and also go in SECRET_NAMES in secrets.py.
  2. Add it to .env.example and give it a description in scripts/handover_b.py (the document build fails if one is missing).
Add an API route
  1. Put it in a router under src/api/routers/ with dependencies=Authed (an unauthenticated route needs a reason), register the router in main.py, and take collaborators (such as the task queue) through Depends so tests can override them.
  2. Test it in tests/integration/test_api.py, including the 401 case; the file already loops over every protected route.
Replace PyGithub with the GitHub MCP server
  1. Implement GitHubContentSource (src/services/github/client.py) and PullRequestService (pr_creator.py) on top of MCP, using fixed call sequences rather than a model-driven tool loop (the locked design).
  2. Swap them in get_content_source() and get_pr_service() in deps.py. Keep tests/contract/test_github_wire.py as the specification of what must be produced; adapt the fake server to the MCP transport.
Point the system at a different LLM
  1. Everything model-specific is in src/agent/nodes/fix_generator.py (LLMClient and the prompts). Change the request or response handling there, update LLM_REQUEST/LLM_RESPONSE in tests/contract/schemas.py, then run the live contract and live evaluation.

Things that already cost time (so they do not cost you time)

  • OSV's CVE-id record has only git ranges; the package data is on its GHSA/GO aliases (fixed in CVEAggregator._fetch_osv).
  • Docker refuses put_archive on read-only containers, and cannot attach a network to a container started with --network none.
  • Grype 0.86.1 could only read a database schema that is no longer updated; keep Grype current.
  • The Redis visibility_timeout must exceed the longest task or Redis redelivers it while it still runs.
  • asyncpg connections and httpx clients cannot cross event loops; Celery tasks therefore dispose them after every task (run_async).
  • PyGithub's call pacing makes a PR creation take about ten seconds, and a GitHub ref is read at /git/ref/… but deleted at /git/refs/….
  • A calibration based on cumulative rates would let strong PRs hide a weak band; each tier is judged on its own band.
